# 実行ワークフロー

このドキュメントでは、APIサービス企画スキルの詳細な実行手順を説明します。

## 実行手順

### 1. 初期ヒアリング

ユーザーから以下の情報を収集：

#### 必須項目

- **サービスのテーマ・分野**: どのような領域のAPIか
- **提供する機能**: どんな機能を外部に提供するか
- **利用者**: 誰が（どのシステムが）APIを利用するか
  - 社内システム連携
  - 外部開発者向け公開API
  - 自社フロントエンド向けBFF（Backend For Frontend）
- **想定リクエスト量**: 初期・将来の規模感

#### オプション項目

- **API形式**: REST / GraphQL / gRPC
- **認証要件**: API Key / OAuth2.0 / JWT
- **SLA要件**: 可用性、レスポンスタイム
- **既存システム連携**: 連携先のシステムやデータベース
- **収益モデル**: 無料 / 有料API / フリーミアム

### 2. アイデアブレインストーミング

#### 2-1. 利用シーンの深掘り

- 利用者（開発者/システム）のペルソナ
- ユースケース分析
- 既存の解決方法と課題

#### 2-2. アイデアの発散

- 3〜5パターンのAPIコンセプトを提案
- 各アイデアの独自性
- 既存APIサービスとの差別化

### 3. 市場・競合分析

#### 3-1. 類似APIの調査

- WebSearchで類似APIサービスを調査
- 競合の機能・価格・ドキュメント品質を分析
- 差別化ポイントの特定

#### 3-2. 市場ニーズの把握

- ターゲット開発者の規模
- 類似APIの利用状況
- APIエコノミーのトレンド

### 4. API設計

#### 4-1. リソース・エンドポイント設計

- リソースの定義
- URLパス設計（RESTful）
- HTTPメソッドのマッピング
- クエリパラメータ設計

| メソッド | パス | 説明 |
|---------|------|------|
| GET | /api/v1/users | ユーザー一覧取得 |
| GET | /api/v1/users/:id | ユーザー詳細取得 |
| POST | /api/v1/users | ユーザー作成 |
| PUT | /api/v1/users/:id | ユーザー更新 |
| DELETE | /api/v1/users/:id | ユーザー削除 |

#### 4-2. スキーマ設計

- リクエスト/レスポンスの構造
- データ型定義
- バリデーションルール
- ページネーション設計

#### 4-3. エラーハンドリング設計

- エラーレスポンス形式
- HTTPステータスコード設計
- エラーコード体系

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid email format",
    "details": [...]
  }
}
```

### 5. アーキテクチャ・インフラ設計

#### 5-1. アーキテクチャパターン

| パターン | ユースケース | メリット | デメリット |
|---------|------------|---------|-----------|
| モノリス | MVP、小規模 | シンプル、開発速度 | スケーリング限界 |
| マイクロサービス | 大規模、複数チーム | 独立性、スケーラビリティ | 複雑性 |
| サーバーレス | イベント駆動、変動負荷 | コスト効率、自動スケール | コールドスタート |

#### 5-2. インフラ設計

- クラウドプロバイダー選定（AWS/GCP/Azure）
- コンピュート（EC2/ECS/Lambda/Cloud Run）
- データベース選定
- キャッシュ戦略（Redis/Memcached）

#### 5-3. セキュリティ設計

- 認証・認可方式
- レート制限
- WAF/DDoS対策
- データ暗号化（転送中/保存時）

#### 5-4. スケーリング戦略

- 水平スケーリング設計
- オートスケーリング設定
- データベースのスケーリング（リードレプリカ等）

### 6. 開発・運用戦略

#### 6-1. 開発フロー

- API仕様ファーストアプローチ
- OpenAPI/Swagger仕様書作成
- モックサーバー活用

#### 6-2. テスト戦略

| テスト種別 | 目的 | ツール例 |
|-----------|------|---------|
| 単体テスト | ロジック検証 | Jest, pytest |
| 統合テスト | API動作検証 | Supertest, httpx |
| E2Eテスト | シナリオ検証 | Postman, k6 |
| 負荷テスト | 性能検証 | k6, Locust |

#### 6-3. 監視・運用

- ログ収集（CloudWatch、Datadog等）
- メトリクス監視（レスポンスタイム、エラーレート）
- アラート設定
- インシデント対応フロー

### 7. 実装ロードマップ作成

#### 7-1. Phase 1: MVP開発（1〜2ヶ月）

- コアAPIの実装
- 基本的な認証
- 開発環境構築

#### 7-2. Phase 2: 本番準備（2〜4週間）

- 本番インフラ構築
- セキュリティ強化
- 負荷テスト
- ドキュメント整備

#### 7-3. Phase 3: 公開・改善（公開後）

- API公開
- 開発者ポータル整備
- SDKの提供（必要に応じて）
- フィードバック対応

### 8. 企画書の作成と保存

全ての分析・設計内容を企画書としてまとめる：

1. 適切なファイル名を生成（例: `api-service-plans/user-management-api.md`）
2. 企画書を`api-service-plans/`ディレクトリに保存
3. ファイルパスをユーザーに通知

### 9. 次のステップの提案

企画完了後、以下のアクションを提案：

- **OpenAPI仕様書作成**: API設計の具体化
- **技術検証**: 主要機能のPoC
- **インフラ構築**: 開発環境のセットアップ
- **開発着手**: 実装開始
- **ドキュメント**: 開発者ポータル準備

## 実行例

### ユーザー入力例

```
ユーザー認証・認可を提供するAPIサービスを作りたいです。
社内の複数サービスで共通して使えるようにしたいです。
OAuth2.0とJWTをサポートしたいと考えています。
```

### 実行フロー

1. 初期ヒアリング（追加質問：想定ユーザー数、SLA要件）
2. アイデアブレインストーミング（3パターン提案）
3. 類似サービス調査（Auth0、Firebase Auth等を参考）
4. API設計（認証、トークン、ユーザー管理のエンドポイント）
5. アーキテクチャ設計（セキュリティ重視）
6. 開発ロードマップ作成（2ヶ月計画）
7. 企画書を`api-service-plans/auth-service-api.md`に保存
8. 次のステップを提案（OpenAPI仕様書作成、セキュリティレビュー）
