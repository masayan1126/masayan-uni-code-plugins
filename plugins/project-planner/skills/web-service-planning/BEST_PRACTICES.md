# ベストプラクティス

このドキュメントでは、Webサービス企画を成功させるためのベストプラクティスと実践的なガイドラインを提供します。

## 企画の原則

### リサーチ重視

#### WebSearch/WebFetchツールを活用
- **競合調査**: 類似サービスを徹底的にリサーチ
- **市場トレンド調査**: 業界の最新動向を把握
- **技術動向調査**: 使用予定の技術の最新情報を収集

#### 実データに基づく判断
- 憶測ではなく、調査結果を基に提案
- 市場規模、競合の価格設定、ユーザー数など具体的な数値を収集
- 業界レポートや統計データを参照

### 実現可能性重視

#### 過度に複雑な機能は避ける
- MVPはシンプルに（コア機能3〜5個に絞る）
- 「あったらいい機能」は後回し
- 「必須機能」のみでサービスとして成立するか確認

#### 既存技術の活用
- 枯れた技術を優先（安定性・ドキュメント・コミュニティ）
- SaaSツールを活用（認証: Clerk、DB: Supabase など）
- 車輪の再発明を避ける

#### 開発期間は現実的に
- 1人開発なら3ヶ月以内のMVP
- チーム開発でも6ヶ月以内を目安
- バッファを20〜30%見込む

### ユーザー中心設計

#### ペルソナの具体化
- 実在しそうな人物像を設定
- 名前、年齢、職業、生活スタイル、課題まで具体的に
- 複数のペルソナを設定し、優先順位をつける

#### 課題解決にフォーカス
- 技術ありきではなく、課題起点で考える
- 「なぜこの機能が必要か」を常に問う
- ユーザーインタビューで仮説を検証

### 柔軟性の確保

#### 段階的な拡張
- MVP（0〜3ヶ月）→ 拡張（3〜6ヶ月）→ スケール（6ヶ月〜）の3段階
- 各段階で学習し、方向転換も視野に入れる
- ユーザーフィードバックを重視

#### 技術選定に代替案を用意
- メイン技術が合わなかった場合の代替案を準備
- ベンダーロックインを避ける
- 技術的負債を最小化

### PWA設計のベストプラクティス

#### モバイルファースト設計

**やるべきこと**
- スマホでの操作性を最優先に設計
- タップターゲットは最低44x44px確保
- 片手操作を意識した下部ナビゲーション
- 下部ナビバーは5項目以内に絞る

**避けるべきこと**
- スマホ画面でのハンバーガーメニュー（到達しにくい）
- 小さすぎるタップターゲット
- 横スクロールが必要なレイアウト

#### アニメーション設計（motionライブラリ）

**やるべきこと**
- ページ遷移を滑らかに（ワクワクする体験）
- インタラクションに適切なフィードバック
- `prefers-reduced-motion`への対応

```typescript
// motion使用例
import { motion } from "motion/react"

// ページ遷移
<motion.div
  initial={{ opacity: 0, y: 20 }}
  animate={{ opacity: 1, y: 0 }}
  exit={{ opacity: 0, y: -20 }}
  transition={{ duration: 0.3 }}
>
  {children}
</motion.div>

// reduced-motion対応
const prefersReducedMotion = window.matchMedia('(prefers-reduced-motion: reduce)').matches
```

**避けるべきこと**
- 過度なアニメーション（パフォーマンス影響）
- 長すぎるアニメーション（ユーザーを待たせる）
- 意味のないアニメーション

#### ナビゲーション設計

**下部ナビゲーションバーの原則**
- 主要機能は5つ以内に絞る
- 6つ以上の場合は「その他」メニューにまとめる
- アクティブ状態を視覚的に明示
- 固定表示でスクロールに追従

```css
/* 下部ナビバー例 */
.bottom-nav {
  position: fixed;
  bottom: 0;
  left: 0;
  right: 0;
  height: 56px;
  padding-bottom: env(safe-area-inset-bottom);
  display: flex;
  justify-content: space-around;
  align-items: center;
  background: #fff;
  border-top: 1px solid #e0e0e0;
}
```

**戻るアイコンの原則**
- 画面左上に常に配置
- 視認性の高いアイコンを使用
- タップ領域は十分に確保（44x44px以上）

#### iPhoneノッチ・セーフエリア対応

```css
/* 必須: viewport-fit=cover対応 */
html {
  padding: env(safe-area-inset-top) env(safe-area-inset-right) env(safe-area-inset-bottom) env(safe-area-inset-left);
}

/* ヘッダー */
.header {
  padding-top: calc(env(safe-area-inset-top) + 12px);
  min-height: calc(env(safe-area-inset-top) + 56px);
}

/* 下部ナビバー */
.bottom-nav {
  padding-bottom: env(safe-area-inset-bottom);
  min-height: calc(env(safe-area-inset-bottom) + 56px);
}
```

#### ホーム画面追加対応

**やるべきこと**
- manifest.jsonを適切に設定
- 複数サイズのアイコンを用意（maskable対応）
- スプラッシュスクリーンを設定
- インストールプロンプトをカスタマイズ

**アイコン作成のポイント**
- maskable対応アイコンはセーフエリア（中央80%）に主要要素を配置
- 背景色は透過ではなく塗りつぶし
- シンプルで認識しやすいデザイン

#### オフライン対応（推奨）

```javascript
// Service Worker登録
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js')
}

// キャッシュ戦略
// - Cache First: 静的アセット
// - Network First: API呼び出し
// - Stale While Revalidate: 頻繁に更新されるコンテンツ
```

## 企画フェーズ別のポイント

### Phase 1: アイデア創出

#### やるべきこと
- 複数のアイデアを出す（3〜5パターン）
- 各アイデアの独自性を明確化
- 類似サービスとの差別化ポイントを特定

#### 避けるべきこと
- 最初のアイデアに固執する
- 競合調査を怠る
- 「誰でも使えるサービス」を目指す（ターゲットが不明確）

### Phase 2: 市場分析

#### やるべきこと
- WebSearchで最低3社の競合を調査
- 市場規模を定量的に把握（TAM/SAM/SOM）
- SWOT分析で自社の立ち位置を確認

#### 避けるべきこと
- 「競合がいない」と思い込む
- 市場規模を楽観的に見積もる
- ニッチすぎる市場を選ぶ（拡張性がない）

### Phase 3: MVP設計

#### やるべきこと
- コア機能を3〜5個に絞る
- ユーザーフローを明確に描く
- データモデルをシンプルに保つ

#### 避けるべきこと
- 機能を詰め込みすぎる
- 技術的に挑戦的すぎる機能を含める
- ユーザーフローが複雑すぎる

### Phase 4: 技術選定

#### やるべきこと
- 開発スピード・コスト・スケーラビリティの3軸で評価
- チームの技術スタックに合わせる
- ドキュメントとコミュニティの充実度を確認

#### 避けるべきこと
- 最新技術に飛びつく（枯れていない技術はリスク）
- 学習コストが高すぎる技術を選ぶ
- オーバーエンジニアリング

### Phase 5: ロードマップ作成

#### やるべきこと
- 各フェーズに明確なマイルストーンを設定
- KPIを定量的に設定
- リスクと対策を洗い出す

#### 避けるべきこと
- 楽観的すぎるスケジュール
- KPIが曖昧（「ユーザーを増やす」ではなく「100人獲得」）
- リスクを軽視

## よくある失敗パターンと対策

### 失敗パターン1: 機能過多のMVP

**症状**:
- 機能が10個以上ある
- 開発期間が6ヶ月を超える
- リリースが遅れる

**対策**:
- 「なくても困らない機能」を削る
- 「後から追加できる機能」は後回し
- MVPの定義を見直す（Minimum Viable Product）

### 失敗パターン2: 市場調査不足

**症状**:
- 競合がいないと思っていたら、実は多数存在
- ターゲット市場が思ったより小さい
- 価格設定が市場とずれている

**対策**:
- WebSearchで徹底的に競合調査
- 類似サービスだけでなく、代替手段も調査
- ユーザーインタビューで市場ニーズを確認

### 失敗パターン3: 技術選定ミス

**症状**:
- 学習コストが高すぎて開発が進まない
- スケールしない技術を選んでいた
- ベンダーロックインで身動きが取れない

**対策**:
- チームのスキルレベルに合わせた技術選定
- スケーラビリティを初期から考慮
- 代替技術への移行パスを確保

### 失敗パターン4: ユーザー不在の企画

**症状**:
- 「自分が使いたい」だけで企画
- ペルソナが抽象的すぎる
- ユーザーインタビューをしていない

**対策**:
- 具体的なペルソナを設定
- 最低10人にインタビュー
- ランディングページで事前に興味を測定

## 成功するための実践的なヒント

### 1. スモールスタート
- 小さく始めて、素早く検証
- Perfect is the enemy of done
- 80%の完成度でリリース

### 2. ユーザーフィードバックループ
- 早期にベータ版を出す
- ユーザーの声を真摯に聞く
- データに基づいて改善

### 3. 継続的な学習
- リリース後もKPIをモニタリング
- A/Bテストで機能を検証
- 競合の動きを常にチェック

### 4. チームとコミュニケーション
- 企画内容をチームで共有
- 定期的に進捗確認
- 方向転換も恐れない

### 5. マーケティングも並行
- 開発中からSNSで発信
- ランディングページで事前登録獲得
- コミュニティを育てる
